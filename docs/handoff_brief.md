### Phase 3 / MVP-A.1 Foundation (13 липня, 4 commits)

**Repo:** github.com/kupolua/church-meeting-assistant, branch `main`

**PostgreSQL:** container `cma-postgres`, port **5433** (5432 зайнятий langfuse-postgres)

**Схема (`db/schema.sql`):**
- `users` — whitelist (Telegram IDs, role='pastor'|'admin')
- `queries` — queue + history (status: pending/processing/completed/failed/cancelled)
- `logs` — T1+T2+T3+T4 events
- `errors` — окремо для alerts
- `health_checks` — 60s snapshots
- Views: `v_queue_depth`, `v_stats_today`, `v_latest_health`

**Ключове про queries table:**
- `verbose_mode` (не `verbose` — reserved word в PostgreSQL)
- `source` = 'web' | 'telegram'
- `telegram_chat_id` + `telegram_message_id` для delivery
- `hits` — JSONB (Hit.to_dict() serialization); `sources` — TEXT[]
- Всі timings (embed_ms, qdrant_ms, rerank_ms, gemma_ms, total_ms)

**RAG service API (`shared/rag.py`):**
```python
result = await rag.answer(question, collection="protocols", limit=5, rerank=True)
# → AnswerResult with .hits, .synthesis, .sources, .timings
# .hits_as_json() для JSONB storage
ret = await rag.retrieve(question, ...)  # без Gemma → RetrievalResult
```

**Logger API (`shared/logger.py`):**
```python
log = Logger(process="bot")
await log.info("event.name", message="...", query_id=..., user_id=...)
await log.record_error(error_type="...", error_message="...", traceback=..., ...)
```

### Meeting-detail: стенограма + аудіоплеєр із таймкодами (22 липня) ✅ закомічено (`927f56a`)

Покращення сторінки зустрічі `GET /meetings/<date>` (`web/routes/meetings.py` + `meeting_detail.html` + `shared/meetings_index.py`):
- **Стенограма** — `annotated.md` парситься в репліки зі спікерами (`_parse_transcript_from_annotated` → `TranscriptTurn`), рендериться **після** переліку тем, згорнута в `<details>`. Лінива група спікера в regex обробляє й плейсхолдери `[немає мовця]` / `[нерозбірливо]`.
- **Аудіоплеєр** — sticky `<audio>` (якщо є `audio.*`), джерело `GET /meetings/<date>/audio` через Starlette `FileResponse` з **нативним HTTP Range** (перемотка без саморобного стрімера).
- **Клікабельні таймкоди** — і в стенограмі (кожен `.turn-ts`), і в темах (дужкові списки, роздільники **кома або крапка з комою**: `(00:21)`, `(24:11, 28:16)`, `(31:30; 33:52; 34:42)`). Клік → seek + play. Хибних збігів (біблійні посилання «Псалом 84:6») уникнуто — лінкуються лише дужкові timestamp-списки.

**⚠ Відома засторога:** у автоматизованому тесті великі m4a (74–103 МБ) інколи повільно вантажили метадані в плеєр (пул зʼєднань браузера, не сервер — curl віддає Range миттєво). У звичайному свіжому браузері працює; якщо на великих файлах буде повільний старт — кандидат на легкий metadata-endpoint / оптимізацію m4a під стрімінг.

### ★ Паролі зникли й усередині церкви (25 серпня) ✅ `d199cec`

Форма «Новий акаунт» більше **не просить пароль**. Акаунт створюється вимкненим із
хешем того, чого ніхто не має, і разом із ним видається одноразове посилання — той
самий `web_invites` (міграція 011), яким засновується церква, на рівень нижче. Разом
із цим закрилось **останнє місце, де секрет ходив із рук у руки**: адмін церкви більше
не знає паролів своїх людей, і не за домовленістю, а за будовою.

**«📩 запрошення» поряд із «🔑 пароль», а не замість.** Скидання — відповідь на «забув,
а треба сьогодні»; запрошення — той самий ремонт без секрету посередині. Обидва в аудиті.

**Двох живих посилань не буває:** нова видача гасить попередню (`expire_pending_for_user`,
`expires_at = NOW()`, а не `used_at` — ніхто його не викупляв, і аудит не має це вгадувати).
Звичайна причина перевидати — що перше пішло не туди, тож лишати його живим означало б
тримати відчиненими саме ті двері, які закривають.

**Викуп веде туди, де людина потрібна:** member → `/dashboard`. `/admin/users` зустрів би
новоприбулого помилкою про права — дивна перша фраза після приєднання.

⚠️ **Вимкнення акаунта не закривало його запрошення — і це знайшлось лише проходженням
потоку в браузері.** `redeem_web_invite` ставить не тільки пароль, а й `is_active = TRUE`;
`deactivate` про запрошення не знав. Прогін на sandbox: створити → видати посилання →
**вимкнути** (`active=false` у базі) → відкрити те саме посилання → `303`, `active=true`,
логін проходить. Поки запрошення існували лише при створенні церкви, це нічого не значило;
щойно їх стало можна видавати живим акаунтам — «вимкнути» перестало бути повним відкликанням.
Той самий урок, що й 25.08 про архів («доступ рветься через усі двері одразу»), просто
застосований до церкви й **не** застосований до акаунта.
Полагоджено в `web_users_repo.deactivate` **одним оператором** (CTE `switched_off` + `killed`):
два послідовні виклики лишають вікно — падіння, обрив, відмова RLS на другому — у якому акаунт
уже вимкнений, а посилання ще робоче, тобто рівно той стан, заради якого все це й пишеться.

⚠️ **Викуп міняв пароль, але лишав відкриті сесії — тобто був слабшим за 🔑-скидання,
хоча панель пропонує їх поруч як рівні.** Скидання гасить сесії з липня («старі сесії не
мають пережити старий пароль»), викуп — ні. Перевірено: сесія, відкрита старим паролем,
після викупу віддавала `200`. Тепер сесії закриваються **у момент викупу**, а не видачі:

### ★ Один вхід, а церква — за потреби (25 серпня) ✅ `834d375`, схема 15

`web_users.username` був UNIQUE **на весь сервер**, тож друга церква, якій потрібен
`pavlo`, мусила вигадувати `pavlo2`. Це була не недбалість: форма входу несе лише
логін і пароль, тож саме ім'я мусило вказувати церкву. Міграція 014 переносить
констрейнт на `(tenant_id, username)`, а питання «яка церква» дістає нову відповідь:
**ім'я, коли воно однозначне, і сама людина, коли ні**.

| ім'я в скількох церквах | що бачить людина |
|---|---|
| 1 (майже завжди) | нічого не змінилось — те саме поле, той самий один хеш |
| 2+ | форма повертається з полем «Церква» і **порожнім** паролем |

⚠️ **Питання ставиться ДО перевірки пароля, і в цьому вся суть.** Спокуслива
альтернатива — перевірити пароль по всіх кандидатах і спитати, лише якщо збігів два —
платить один scrypt за кандидата на кожен здогад, випробовує цей здогад одразу на
кількох людях і робить саму появу питання **доказом того, що пароль правильний**.
Які церкви існують — не таємниця такої ціни; чи правильний пароль — таємниця.
У наборі це прибито: **невірний** пароль дістає те саме питання. Ця перевірка падає
тієї ж миті, коли хтось перепише потік навпаки.

**Решта форми — кожна деталь тому, що без неї щось ламається:**

- Невірна церква відповідає **точно як невірний пароль** (те саме повідомлення, той
  самий статус, той самий спалений scrypt) — інакше поле стає способом спитати «а чи
  є це ім'я **в тій** церкві?».
- Пароль **не повертається** у перемальовану форму. Hidden-поле поклало б його у код
  сторінки, в історію браузера й у кожну сторінку помилки; одне зайве набирання дешевше.
- Поле — **вільний текст, не `<select>`**: список вибору роздав би кожному відвідувачу
  перелік усіх церков сервера.
- Крок із питанням **витрачає** бюджет гальма, інакше він безкоштовний оракул «чи є це
  ім'я більш ніж в одній церкві».
- Питається **ідентифікатор** (назву можна перейменувати), і людина його бачила:
  сторінка запрошення показує «Церква `<slug>`» саме тоді, коли вона задає пароль.
  Назва теж приймається — поки вказує на одну церкву.

⚠️ **Знятий констрейнт був ще й єдиним індексом по `username`.** Без заміни кожен вхід
став би послідовним скануванням `web_users` — повільним пізніше й у спосіб, якого ніхто
не зв'язав би з цією міграцією. У 014 додано окремий `idx_web_users_username`.

⚠️ **Назад дороги немає, щойно нею скористаються.** Коли дві церкви візьмуть однакове
ім'я, стару глобальну унікальність уже не створити. Відкат після цього — не `git revert`,
а ручне перейменування людей.

**Тести: 153 → 169.** Дві наявні перевірки **інвертовано** — вони стерегли протилежне
(«логін, зайнятий в іншій церкві, відхиляється» і «username stays globally unique»).
Кожну нову прогнано проти навмисно зламаного коду — прибрано питання; питання після
пароля; окреме повідомлення для невірної церкви; пароль повернуто hidden-полем; список
церков дописано в підказку — **усі п'ять зловлено**.

⚠️ **Набір не ідемпотентний:** тест архіву вимагає порожнього «Архіву», тож sandbox треба
**перезбирати перед кожним прогоном**. Три прогони поспіль по одній базі дають хибне
падіння, яке виглядає як регресія.

**Викочено за §11 ранбука:** бекап → push+pull під `cma` → міграція **від root** (`cma`
її застосувати не може за побудовою) → рестарт web. Звірка не лише `GET /login → 200`,
а й `POST /login` з неіснуючим логіном: **401**, а не 500, тобто `resolve_login_tenant`

## Run-модель (важливо — 4 процеси одночасно)

```
web / Telegram-бот  →  INSERT pending (queries)  →  worker → RAG → completed → delivery
web /ingest         →  INSERT pending (ingestion_jobs) → ingestion-worker →
                         transcribe → [PAUSE: web-редактор speakers] → analyze → index
                                                    ↕
                                  dashboard: live-моніторинг + дії
```

**Одна команда** піднімає все (перевіряє контейнери+Ollama, рестартує 4 сервіси у фоні):
```bash
./restart_dev.sh          # web + bot + query-worker + ingestion-worker; логи в logs/
./restart_dev.sh --stop   # зупинити сервіси + контейнери
```
Без query-worker'а запити висять у `pending`; без ingestion-worker'а завантажене аудіо висить у `pending`. Мають бути up: **Ollama з `gemma4:26b` ТА `bge-m3`** (`ollama pull bge-m3`), Qdrant, Postgres. `VOYAGE_API_KEY` більше **не потрібен**.

*(Терміналами вручну — ті самі 4 команди: `uvicorn …web.main:app`, `-m …bot.main`, `-m …worker.main`, `-m …ingestion.main`.)*

**Примітка:** контейнери на M1 інколи «відпадають» після сну машини — `restart_dev.sh` їх піднімає.

**⚠️ Схема вище — для однієї машини. У продакшні з 24.08 усе розʼїхалось:**

```
церква → https://cma.rechurch.org.ua (VPS: web, bot, Postgres, Qdrant, артефакти)
                        │  WireGuard 10.10.0.1 ↔ 10.10.0.2
                        ▼
                   M1 (CMA_ROLE=worker): Ollama + query-worker + ingestion-worker
```

На M1 у `.env` стоїть `CMA_ROLE=worker` — `restart_dev.sh` піднімає **лише два воркери**,
локальних контейнерів не чіпає (вони на VPS) і перевіряє їх через тунель. `--stop` при цьому
гасить **усі** сервіси, включно з web і ботом від попереднього запуску в ролі `all` — інакше
ноутбук тихо обслуговував би базу, яку решта системи вже покинула. web і Telegram-бот — це
systemd-юніти на VPS (`deploy/systemd/`).

⚠️ **`.env` на M1 має дублікати ключів** (початкові `DB_HOST=127.0.0.1:5433` угорі, VPS-овські
внизу). `python-dotenv` бере **останнє** визначення — і `restart_dev.sh` тепер теж (`tail -1`).
Якщо зводити їх докупи, то за один раз, а не наполовину.

Без `CMA_ROLE` поведінка не змінюється ані на йоту — одна машина працює як раніше.

**Після мультитенантності:** веб більше не анонімний — усе, крім `/login` і `/static`, вимагає сесії

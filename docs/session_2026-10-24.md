## Рішення, які не варто переглядати без Pavlo

- **Код → потім схвалення**, не навпаки: до власника доходять лише живі адреси.
- Безкоштовний пробний план — беклог п.12 (`handoff_brief.md`), не робити до
  обговорення: 120 хв, 24 год, одна зустріч, звірка голосів між пробними акаунтами.
- Обовʼязкові підписанти = учасники, чиє імʼя збігається з «Присутні» у протоколі;
  всі підписали → затверджено автоматично; ведучий/адмін може затвердити вручну.
- Підпис над SHA-256 канонічного тексту (`shared/protocol_hash.py`); правка
  тексту робить підпис «застарілим», не видаляє.
- Запрошеного учасника немає як окремого шляху: він просто «Увійти» за кодом.
- Pavlo тестує на своїх телефонах, оновлюючи APK поверх; емулятор на Mac — для
  Claude. Після кожної зміни застосунку: підняти `version:` у `app/pubspec.yaml`,
  `app/build_apk.sh`, назвати файл. Зміни лише на сервері — APK не потрібен.

## Як працювати далі

**Локальний стенд.** Postgres у контейнері `cma-dev-postgres` (порт 5434, `cma`/devpass,
`cma_app`/devapp, схема 24, тенанти 1 `default` і 3 `hope-church-kyiv`, акаунти
`pavlo@example.org`, `ihor@example.org`, `olena@example.org`). Сервер:

    source ~/.claude/jobs/<job>/tmp/dev.env   # DB_* на 5434, CMA_ROLE=web
    export DATA_ROOT=$PWD/data                 # справжні теки ReChurch для tenant 1
    uv run uvicorn church_assistant.web.main:app --port 8010
    # коди входу без SMTP: grep "code for" у логу

Застосунок на емулятор: `flutter build apk --debug --dart-define=CMA_API=http://10.0.2.2:8010`
з теки `app/`. Емулятору потрібно 4 ГБ RAM; між tap і text в adb — 3 с; BACK на
корені виходить із застосунку; `flutter build` з паралельних викликів плутає cwd —
запускати послідовно або через `(cd app && …)`.

**Викочування.** `docs/vps_deploy.md` §11: бекап → `git pull` від `cma` →
міграція від root → `systemctl restart cma-web` → проба `https://cma.rechurch.org.ua/api/v1/me` (401 без токена).

**Сервер обробки «ai»** (DL165 G7 у церкві, 10.10.0.3 через VPS): конвеєр там,
цієї сесії не чіпали.
